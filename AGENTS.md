# workflow

This directory holds a personal work-management system: the design (`WORKFLOW.md`), four agent workflows in `prompts/`, and thin adapters so the same workflows run in Claude Code or GitHub Copilot. The live data is in the Obsidian vault, not here.

## Workflows

| Workflow | Instructions | Claude Code | Copilot | Touches |
|---|---|---|---|---|
| standup | `prompts/standup.md` | `/standup` | agent `standup` | vault notes; Jira read-only |
| weekly | `prompts/weekly.md` | `/weekly` | agent `weekly` | vault notes; Jira read-only, lists writes for `apply` |
| prreview | `prompts/prreview.md` | `/prreview` | agent `prreview` | vault notes; Bitbucket and GitHub read-only |
| apply | `prompts/apply.md` | `/apply` | agent `apply` | Jira writes, each one shown and confirmed first |

The prompt files are the source of truth. The adapters (`.claude/commands/*.md`, `.github/agents/*.agent.md`) only declare the tools and point at the prompt. Edit the prompt, not the adapters. Prompts refer to the workflows by their Claude names (`/standup`, `/apply`); in Copilot that means the custom agent of the same name.

## Tool naming

The prompts name MCP tools as `<server> <tool>`, for example Jira `search_issues` or Bitbucket `get_pr_diff`. The same tool is spelled `mcp__jira__search_issues` in Claude Code and `jira/search_issues` in Copilot. The servers are [RAVEN](https://github.com/bcgov/raven)'s, registered as `jira`, `bitbucket` and `github`; if you registered them under other names, change the adapters' tool lists, not the prompts. `jira list_deployment_slots` is specific to a deployment-booking add-on; drop it if your Jira has no such tool.

## Rules for any agent working in this directory

- Jira is the system of record for team-visible work. The vault holds only what Jira cannot: the user's next action per workstream, waiting-for, and uncommitted captures.
- prreview is read-only against Bitbucket and GitHub and never posts; it runs with read-only PR tools because PR text is untrusted input.
- standup is read-only against Jira. apply and weekly may write to Jira only after listing the exact calls and getting an explicit yes; a ticked box in Proposed is not that yes.
- standup sets `last_touch` from Jira activity without asking. Every other workstream change (`tickets`, `waiting_on`, `next_action`, `status`, new notes) happens only when the user has ticked it in Proposed, or approved it in an interactive standup or weekly.
- Keep workstream frontmatter valid YAML: quote strings that contain colons or quotes; `tickets` is a flow list `[KEY-1, KEY-2]`; dates are `YYYY-MM-DD`.
- Every Jira key written into a vault markdown body is a link to `https://jira.example.com/browse/KEY`. Frontmatter `tickets` stays plain keys.
- Never read, cat, grep or summarise `Workflow/Email tasks.md` or the mail drop folder, by any tool. Work email stays out of the agent. Claude Code enforces this in `.claude/settings.json`; in Copilot it is this rule plus never adding the mail folder with `--add-dir`. Never write to `Email tasks.md` either: only the bash script may.

## Host notes

- **Claude Code**: `CLAUDE.md` imports this file. The commands in `.claude/commands/` inline the prompt with `@prompts/<name>.md` and pass `$ARGUMENTS` (`--scheduled` from the runner).
- **Copilot CLI**: the runner calls `copilot --agent <name> -p "... --scheduled" --allow-all-tools --add-dir "<vault>"`. Non-interactive mode needs `--allow-all-tools`, so the tool restriction comes from the agent file's `tools:` list, not from the CLI.
- **Copilot in VS Code**: open this folder, add the vault folder to the workspace so the agent can read and write it, pick the agent in the chat agent picker and send `run` (or `--scheduled` to simulate the morning job).
